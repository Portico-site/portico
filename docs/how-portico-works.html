How this whole thing actually works

Every concept behind Portico, in the order that makes them make sense — with questions to test yourself, so you find out what you actually know rather than what merely looked familiar.

00The one-paragraph version

Portico is a desktop app that talks to a language model running on your own computer. It has three layers: a window that draws the chat, a controller that manages files and processes, and an engine — a separate program that does the actual thinking. The window never talks to the engine directly. Everything you add to the app is one of those three layers, or a message passing between them.

If you remember nothing else, remember that shape. Almost every question — "where does this code go?", "why can't the page do that?", "why did it break?" — is answered by knowing which layer you are in.

01The shape of the app

Portico is built with Electron, which is a way to make a desktop app out of web technology. An Electron app is really two programs running at once.

The two halves

HalfWhat it isWhat it can do
Main processNode.js. No window. Read and write files, start other programs, make network requests, create windows.
RendererA web page — HTML, CSS, JavaScript. Draw the interface, handle clicks. Cannot touch your disk or start programs.

That restriction is deliberate. The renderer runs web-page code, and web pages are not allowed to read your hard drive. So when the interface needs something real to happen — save a chat, start the engine, download a model — it has to ask the main process.

How they talk: IPC

IPC means inter-process communication: messages between the two halves. Portico has 60 of these message handlers. It works like ordering at a counter:

renderer                    preload bridge              main process
  |                              |                            |
  | api.saveChat(chat) --------> | ipcRenderer.invoke -------> | ipcMain.handle('save-chat')
  |                              |                            |   writes the file
  | <-------------------------- result <---------------------- |

The middle column is the preload script — preload.js. It is the only thing both halves can see, and it publishes a fixed list of 72 permitted calls as window.pristudio. The page cannot invent new ones. If a feature needs something the bridge does not expose, you add it in three places: a handler in main.js, a line in preload.js, and a call in app.js.

Found the hard way

Electron bans window.prompt(). Clicking "New project" silently did nothing for weeks because the exception was swallowed. This is the layer boundary biting: the renderer is a web page, and Electron removes browser features that would block its process. confirm() still works; prompt() does not.

Check yourself
Why can't the chat window just write your chat file directly?

Because it is a web page. Web pages have no file access — that is a security rule of the browser engine Electron is built on. The renderer must ask the main process, which is ordinary Node.js and has no such limit.

You want a button that opens the user's Downloads folder. Which files do you touch?

Three. A handler in main.js (it does the opening), an entry in preload.js (to permit the call), and the button plus its click handler in app.js. Miss the preload line and the page will report the function does not exist.

Something works when you run npm start but fails in the installed app. What kind of bug is that likely to be?

A packaging problem, not a logic problem. In development the app reads loose files; once installed it reads a bundled archive. Anything that assumed a path, or a library that was not included in the bundle, breaks only after packaging. This exact thing happened here — a library used by the preload script was listed as a development-only dependency, so the bridge failed silently in the installed build.

02The engine

Portico does not contain a language model, and does not do the maths itself. It ships a separate program called llama-server, from the open-source project llama.cpp. When you load a model, Portico starts that program as a child process and then talks to it over the network — on your own machine, at 127.0.0.1:8033.

That address means "this computer only". Nothing leaves the machine.

Why a separate program

  • If the model crashes, the app does not. Portico notices the process died and reports why.
  • llama.cpp speaks the same request format as commercial AI services, so the same code can talk to a local engine or a remote one — which is exactly how the shared engine works.
  • llama.cpp is maintained by other people, and improves without Portico changing.

The request

A chat request is a list of messages with roles, sent as JSON:

POST http://127.0.0.1:8033/v1/chat/completions
{
  "messages": [
    { "role": "system", "content": "instructions the user never sees" },
    { "role": "user",   "content": "what is a portico?" }
  ],
  "stream": true,
  "temperature": 0.4,
  "max_tokens": 1024
}

stream: true means the reply arrives word by word instead of all at once — that is why text appears as it is written. The system message is instructions the model receives but you never see; Portico builds it from your saved prompt, any project instructions, and situational guidance.

Design decision

This request is made by the main process, not the page. Two reasons: the access key for a shared engine never reaches the page, and the page's security policy can stay locked to "this computer only" instead of being opened up to arbitrary addresses.

Check yourself
If the engine is a web server, could someone else on your Wi-Fi use it?

Not by default. It listens on 127.0.0.1, which only accepts connections from the same machine. It becomes reachable only if you deliberately switch on sharing, which changes the address to 0.0.0.0 and requires an access key.

The reply appears all at once instead of word by word. What changed?

Streaming is off, or the streamed pieces are not being forwarded to the page as they arrive. The request is the same either way — stream just decides whether the engine sends one response or a series of fragments.

Why can the same code talk to your laptop's engine and to a colleague's?

Because it is an ordinary HTTP request, and the only difference is the address. Local is 127.0.0.1:8033; a colleague's machine is 192.168.1.40:8033. Everything else is identical.

03Models and what the numbers mean

A model is a large file of numbers — the weights. Portico uses the GGUF format, which is what llama.cpp reads. Your catalogue has 34 of them.

Parameters: the "7B"

7B means seven billion weights. More weights generally means better answers and a bigger file. It is a rough guide to capability, not a guarantee — a good 7B beats a bad 13B.

Quantisation: the "Q4_K_M"

Weights are naturally stored at 16 bits each. Quantisation stores them with fewer bits, which shrinks the file dramatically at a small cost in quality.

LabelBits7B modelVerdict
F1616~14 GBOriginal. Rarely worth it.
Q8_08~7 GBPractically identical to the original.
Q4_K_M~4.5~4.7 GBThe default. Best size-to-quality trade.
Q3_K_M~3.5~3.5 GBNoticeably worse, but fits where Q4 will not.

Mixture of Experts: the "30B-A3B"

Most models use every weight for every word. A Mixture of Experts model splits part of itself into several "experts" and uses only two of them per word, chosen by a small router.

So Qwen3-30B-A3B means 30 billion total, 3 billion active per word. The crucial consequence:

  • Speed follows the active number — it runs like a 3B model.
  • Memory follows the total number — all 30B must be loaded, because the router may pick any expert at any moment.

Older names like Mixtral 8x22B mean the same thing but hide it: 8×22 is 176, while the model actually has about 141 billion weights, because only part of it is duplicated.

Vision

A model that can look at images needs a second file, a projector (mmproj-*.gguf), which turns pictures into something the model can read. Portico pairs them automatically by matching the longest shared run of characters in their filenames — which is why a projector for one model will not be wrongly attached to another.

Check yourself
You have 16 GB of memory. Is a 30B-A3B model a good fit?

No. Only 3B is active per word, so it would feel fast — but all 30B must fit in memory first, which at Q4 is about 17 GB. Mixture of Experts saves computing time, never memory. When memory is your limit, it is the wrong shape of model.

Which is likely better: a 13B at Q3, or a 7B at Q4? Both about 5 GB.

Usually the 13B at Q3 — more knowledge, coarsely stored, tends to beat less knowledge stored precisely. But it is genuinely close, and below Q3 quality falls away quickly. This is worth testing rather than assuming.

Your model ignores an image you attached. First thing to check?

Whether the model has a projector file and whether that model is the one currently loaded — not merely selected in the dropdown. Without a projector the image is silently dropped.

04Your hardware

Three kinds of memory matter, and they are not interchangeable.

WhereYoursSpeedRole
VRAM4 GB~200 GB/sOn the graphics card. Fastest. Smallest.
RAM15.3 GB~50 GB/sSystem memory. The practical limit on model size.
SSDlarge~5 GB/sStorage. Roughly ten times slower than RAM.

Offloading

A model is made of layers. llama.cpp puts as many as fit into VRAM and runs the rest on the processor. A 4.7 GB model on a 4 GB card is not an error — most of it runs on the card, the remainder on the processor, and it is slower than if it all fitted.

Can the SSD substitute for memory?

It already does, and it is not a solution. The engine memory-maps the model file, so a model larger than your memory still loads — the system pages pieces in from disk as needed. But producing a single word requires reading essentially every weight. At SSD speed that is around a second per word. It prevents a crash; it does not give you a usable model.

Measured here

Portico used to assume the discrete graphics card was the fastest and always chose it. On this laptop that was wrong: the driver had powered the card down, and the built-in graphics measured 15.1 words per second against the "better" card's 3.4.

So a benchmark was added. It then made the opposite mistake — it ranked purely on speed, and picked the built-in graphics, which turned out to produce pure gibberish: one character repeated. It now checks that a device produces coherent text before considering how fast it was. Speed is worthless if the words are wrong.

Check yourself
Would a faster SSD let you run bigger models well?

No. Even a fast SSD is roughly ten times slower than RAM, and every word needs nearly the whole model read. More RAM is the upgrade that changes what you can run; a faster disk only shortens loading.

Name three ways to fit more of a model into 4 GB of VRAM.

Lower the context size (the conversation's memory occupies VRAM too); use a smaller quantisation so more layers fit; or store the conversation memory itself in a compressed form. For Mixture of Experts models specifically, the engine can also keep the experts in system RAM and run only the attention part on the card.

Why is "the fastest device" the wrong thing to measure?

Because a device can be fast and wrong. That happened here — the quicker graphics device returned repeated characters instead of words. Correctness has to be confirmed before speed means anything.

05The context window

This is the concept that explains most "why is it being stupid" moments. Learn this one properly.

A model has no memory. It does not recall your last message. Every single time you press send, Portico re-sends the entire conversation, and the model reads all of it fresh. The context window is the maximum amount it can read at once.

Tokens

Text is measured in tokens, roughly ¾ of a word. Portico estimates 3.6 characters per token — approximate, but stable enough to budget with.

The budget

Your context is not all available for conversation. Room must be reserved for the reply, because the answer has to fit in the same window:

context size          4,096 tokens
reserved for reply   -1,024
overhead               -300
                     -------
room for conversation 2,772 tokens

When the conversation exceeds that, Portico drops the oldest messages. It does not warn loudly — the ring in the strip below the message box turns amber, and the panel tells you how many were dropped. That is why a long conversation starts forgetting how it began.

Found the hard way

Early on, every past message re-sent its full retrieved web-search text. Three searched questions consumed 7,237 of 8,192 tokens — 88% — so the model lost the conversation entirely and follow-ups answered nonsense. Now only the message being answered carries its full text; older turns collapse to a one-line summary.

Why bigger is not free

The conversation is held in something called the KV cache, and it lives in the same VRAM as the model. Raising context from 4,096 to 65,536 can consume gigabytes — which pushes model layers off the graphics card and makes everything slower. Context size is a trade, not an upgrade.

Check yourself
You say "my name is Ana", then thirty messages later it has forgotten. Why?

The context filled and the oldest messages — including that one — were dropped to make room. The model is not forgetting; that text is no longer being sent to it at all.

Raising context from 4,096 to 32,768 makes replies much slower. Is that a bug?

No. The conversation's memory grew and now occupies VRAM that the model was using, so fewer layers fit on the graphics card and more runs on the processor. It is the expected cost.

Why does setting a longer maximum reply reduce the room for conversation?

Because the reply must fit in the same window. Room is reserved before history is packed. Ask for a longer possible answer and you have reserved more, leaving less for what came before.

Attaching a large PDF makes it forget everything else. Why?

The document's text goes into the same budget. A long PDF can consume most of it, crowding out the conversation. Portico trims attachments to a share of the budget for exactly this reason.

06How each feature works

Web search

Models know nothing after their training date and cannot browse. Search works in four steps: decide whether to search; turn your message into keywords; fetch results from several sources at once; paste the text into the request so the model can read it.

The important finding from building it: search pages block automation, but APIs and news feeds do not. Wikipedia, Marginalia, Google News, Stack Overflow, arXiv and Polymarket all work without a key; ordinary search-engine pages return challenges instead of results. Search is off by default, because it is the one thing that sends your words off the machine.

Projects and assistants

A project is standing instructions plus reference files, applied to every chat inside it. An assistant is a saved persona plus generation settings. Project material is capped at 30% of the character budget so it cannot crowd out the conversation.

Artifacts

When the model writes a web page, Portico can render it. The page is written to disk and shown in a frame that is deliberately isolated — it can run scripts, but it cannot read anything belonging to Portico.

Found the hard way

The chat settings panel appeared completely blank. The panels hide by sliding out of view with a negative margin — but a hidden panel still paints, and the artifact panel's empty frame was drawing straight over the settings. The white rectangle was an empty web page sitting on top. Fixed by making a closed panel genuinely stop painting.

Running Python

Code blocks get a Run button. It never runs by itself, the code is scanned for risky operations first, and it stops after 90 seconds. Charts are captured and shown in the conversation.

Portico also sets chart styling defaults, because matplotlib's own defaults are from 2003 and are the main reason generated charts look dated. It repairs old style names too — models still write seaborn-whitegrid, a name removed from matplotlib in version 3.6, which used to crash the whole snippet.

Image generation and voice

Both are separate bundled programs, like the chat engine. Image generation downloads on demand because it is large; because the chat model and the image model cannot share 4 GB of VRAM, Portico stops the chat engine, renders, then restarts it.

Check yourself
Why is web search off by default in an app that promises privacy?

Because searching necessarily sends your words to someone else's server. Everything else happens on your machine, so this is the single exception and it should be a deliberate choice, not a default. The app also says on screen whenever it is on.

You ask "tell me more about him" and get nonsense. What is going wrong?

A follow-up has no subject of its own. If it is treated as a fresh search query, "tell me more about him" is searched literally and returns unrelated pages. It has to reuse the topic from the previous turn — which is exactly the bug that was found and fixed here.

Why does generating an image unload your chat model?

They cannot both fit in 4 GB of VRAM. Portico stops the chat engine, generates, then restarts it — which is why the model reloads afterwards.

07The shared engine

One computer with a good graphics card can run the model for everyone else on the network. The same app is both host and client — it is a mode, not a separate product.

This works because the engine was already an HTTP server. Sharing changes its address from "this computer only" to "reachable on the network", and requires an access key.

Only the thinking is shared. Chats, files and projects stay on each person's own machine, so the host never becomes a store of everyone's history.

Found the hard way

Two things nearly shipped broken. The "test connection" button checked an address that llama.cpp deliberately leaves unprotected, so it reported success even with a wrong key. And sharing with several people would silently have given each of them a fraction of the configured conversation memory, because the engine divides context across simultaneous users.

Check yourself
Four people share one engine. What does the host need more of?

VRAM. Each simultaneous conversation needs its own slice of memory for its history, on top of the model itself. The processor is rarely the limit; memory is.

Is it safe to open this to the internet?

No. Traffic is unencrypted, so it belongs on a network you trust. For access from outside, the right tool is a VPN — not forwarding the port.

08Building and shipping

Writing code and shipping an app are separate acts. npm run release builds the installer and copies it where the website expects it — both, because they used to drift apart.

TermMeaning
electron-builderTurns the source into a real installer.
asarThe archive your code is packed into. Loose files at build time, one bundle after.
extraResourcesFiles copied in beside the bundle — the engine binaries, which must stay real files.
code signingA paid certificate proving who published the app. Without it, Windows warns.
auto-updateCompares your version against a published release. Inactive until the project is published.
Found the hard way

A whole session's work appeared to have vanished. The builds went to the project's output folder, while the Start menu still opened the version installed three days earlier. Building is not installing. Worse, two different builds can both call themselves 0.20.0 — so version numbers are not proof of contents.

Other platforms

The JavaScript is already portable. What differs per system is the engine binaries, which are compiled per platform. Chat works everywhere; voice and image generation are Windows-only for now, because those projects do not publish ready-made Mac or Linux builds.

Check yourself
You changed a file and rebuilt, but the app behaves the old way. Two likely causes?

You are opening the installed copy rather than the newly built one; or an old copy is still running and the app's single-instance rule simply focused it instead of starting the new one.

Why do the engine binaries sit outside the code bundle?

Because they are programs that must be launched, and you cannot launch a file that only exists inside an archive. They have to remain real files on disk.

09How it is tested

Seven suites drive the real, installed application — not a simulation. They connect to the running app the way browser developer tools do, then click things and read what happened.

SuiteCovers
full-suite83 checks across every feature
e2e-flows19 real journeys — actual search, vision, Python, images
networkThe shared engine, verified from outside the app
status-stripModel, effort and context controls
panels · sidebar · chat-settingsInterface regressions

The lesson worth carrying: a test that fails is not automatically a broken product, and a test that passes is not automatically a working one. Several "failures" here were faults in the test itself — a slider that snaps to steps, a wait too short for a delayed save. But one apparent flake was real: the search tests began returning gibberish, which turned out to be the graphics-device bug. Investigate before dismissing.

Check yourself
Why test the installed app rather than the source?

Because the packaging step is itself a source of bugs. Testing the source would miss exactly the class of problem that only appears once the app is bundled and installed.

11Directing me well

You asked for this guide so you could steer better. Here is what actually changes the outcome.

Say the symptom, not the diagnosis

You are better placed to describe what you saw than to guess the cause — and a wrong guess sends me down the wrong path. "Chat settings don't work" was perfect: it led to the real cause, an invisible frame painting over the panel, which no theory of mine would have reached first.

Vaguethe chat is broken
Usefulwhen I open chat settings the panel is blank — the title shows but nothing under it. Started after the last build.

Paste the error

The seaborn-whitegrid traceback you pasted took about a minute to diagnose. Described in words it could have taken twenty. Full error text is the highest-value thing you can give me.

Name the layer or the file

Now that you know the shape, use it. "In the composer" or "in websearch.js" removes all the searching.

Vaguemake the search better
Usefulin websearch.js, add a source for recipes, and keep Wikipedia working

Say what must not change

This one saves the most rework. "Fix the alignment without touching the animations" tells me where the fence is. Without it I may improve something you were happy with.

Give me a reference, or say what "better" means

The screenshots you sent were far more effective than any description. If you have no reference, name the quality: "smaller", "less cramped", "like a terminal status bar".

Separate asking from building

"Just asking, don't change anything yet" is genuinely useful — you get an answer without changes you did not want. Equally, "do it" is a clear instruction to stop discussing.

Ask me to prove it

"How do you know?" is a fair and useful question. Twice in this project a confident change was wrong — the graphics benchmark that chose a device producing gibberish, and a "fix" to an escaping bug that did not exist. Measurement beats reasoning, and you are entitled to see the measurement.

A template that works

What I see — the symptom, or the error, pasted in full.
Where — the screen, the feature, or the file.
What I want — the outcome, not the implementation.
What not to touch — anything you are already happy with.

Check yourself
Rewrite: "the models are bad"

Something like: "Qwen 7B gives short, shallow answers to coding questions, while Llama 3B answers the same ones well. Nothing else changed. Is this the model, or a setting?" — it names what, compares against something, and asks a real question.

You want a change but fear breaking things. What do you add?

The fence, and a request for proof: "add X, don't change the composer layout, and run the tests afterwards."
